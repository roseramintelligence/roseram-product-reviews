## A spatial record needs stable meaning, not only geometry

The homepage describes walls, doors, rooms, desks and assets as nodes with relationships in a Space Graph. That model can be useful when different systems need to refer to the same room or workstation. However, a geometric object and an operational entity are not always the same thing. A room may be divided, renamed or reassigned without every connected system changing in the same way. Define which identifiers remain stable and which changes create a new entity before relying on the graph as an organizational reference.

For example, a booking system may recognize a room by one identifier while a facilities team uses another naming convention. The value of a shared record depends on maintaining that mapping through edits. This is an illustrative data-management problem, not a configuration inspected here. A browser editor can make changes convenient, but the business still needs rules for what the edited objects mean and who is responsible for resolving disagreements between the drawing and operational systems.


## Onboarding quality depends on the source plan

The captured pricing accepts JPG, PNG, PDF, DWG and DXF inputs and describes white-glove conversion involving people. That is an important distinction from assuming every upload becomes an accurate model without review. A scanned plan, an old CAD file and a current verified drawing can carry different uncertainties. Establish which source represents the actual building, what detail it contains and what the conversion team is expected to preserve or reconstruct.

Choose a pilot floor with representative complications rather than only the simplest rectangle. Review room boundaries, doors, labels, desks and any dimensions the downstream workflow depends on. Record unresolved ambiguities before accepting the converted plan. These are proposed acceptance checks, not observations from a conversion conducted here. Human-assisted onboarding can provide a review process, but its existence alone does not certify the source drawing, the physical building or every measurement used by a connected application.


## Per-floor pricing should be evaluated as a portfolio commitment

Confirm the number of plans, the annual charge and how the agreement handles additions, replacements or archived floors.

Those are different commercial arrangements, not a single universal entry price. Compare the actual route needed for the project. Write a requirement list with the exact editing, integration and development capabilities needed. A facilities team using one workplace connection has different needs from a software company embedding interactive plans for customers. Check the applicable agreement rather than infer entitlement from a feature appearing elsewhere on the website. The saved table is useful evidence of packaging differences, but this review has not verified an account's permissions or purchased add-ons. ## Browser editing needs a change-governance process

Archilogic describes autosave, revision history, visual differences and rollback. Those functions can make plan maintenance more accessible than editing a separate CAD artifact for every update. They do not decide when a proposed layout becomes the official operating record. An experimental seating plan and a completed physical rearrangement should not accidentally be treated as the same state by downstream systems. Define draft, approved and published meanings before multiple teams begin editing.

The Professional pricing mentions a layout-change approval flow, which is a relevant feature to investigate for that requirement. Test who can propose, approve and publish a change and what a connected system sees at each stage. These are proposed checks, not exercised permissions. A rollback should also be understood as a data operation with downstream consequences, not merely a comforting button. Restoring the drawing may require connected systems to reconcile changes they have already consumed.


## Custom attributes need an owned schema

The product page describes attaching custom attributes to spaces, assets and floors and using a spreadsheet-like interface to search, filter and edit metadata across a portfolio. This could help represent business-specific information without making separate spreadsheets the only source. The challenge is consistency. If one team labels a space by department and another by booking category, the model needs clear fields rather than a single ambiguous text value that different integrations interpret differently.

Define allowed values, ownership and the meaning of a blank field. Decide whether a field describes the physical space, its current use or a planned future configuration. These recommendations are not claims about a schema feature tested in Archilogic. They are necessary preparation for any shared operational record. The platform's ability to store custom data is useful only when teams can understand and maintain that data without silently changing the meaning of reports or connected application behavior.


## Integrations require identifier and synchronization checks

The homepage lists workplace and property-technology connections, while the pricing FAQ specifically points to guidance for mapping Microsoft Places identifiers and producing compatible exports. That mapping step is important: two systems can describe the same room without automatically sharing its identity. Confirm how initial matching works, how changes are detected and what happens to references when a space is removed or split. A named integration is a starting point, not proof that a particular organization's existing data will match cleanly.

The product page says webhooks fire on publish, update and delete. An integration consuming those events still needs an understandable response to duplicates, delayed processing and an unavailable downstream system. These are proposed design scenarios rather than observed faults. No webhook was sent here. The appropriate acceptance result is a consistent record in the connected application after a representative edit, including a documented way to reconcile exceptions rather than an assumption that every system remains current automatically.


## Exports and live connections have different maintenance models

The pricing notes list export formats including image, drawing, geographic and 3D formats, while the product page also describes PDF and DWG sharing paths. An exported file is a snapshot of a record at a particular time. A connected application may instead expect the current state. Decide which route suits the recipient and label exports with the relevant version or date. Otherwise an old file can continue circulating while teams believe they are looking at the maintained record.

Check the exported result in the actual receiving tool, especially if it depends on identifiers, metadata or geometric interpretation rather than appearance alone. A file opening successfully is not the same as preserving every attribute the workflow requires. These are proposed checks, not exports performed in this review. The source lists available paths but does not establish fidelity for every combination of source plan, export format and downstream application. Evaluate the specific exchange that matters to the project.


## Public sharing, private links and embedded plans need clear boundaries

The product material describes public and private sharing URLs and origin-locked embeds. These are useful distinctions for a building record that may be shared with occupants, contractors or the public. A public marketing floor plan and an internal operational layout can contain different levels of detail. Decide what the audience should see before selecting the sharing route. Do not assume a link is appropriate merely because it is convenient to distribute.

For an embedded application, verify the intended origin and the data accessible to the viewer. Review whether custom attributes or sensitive asset locations are included in the experience. These are proposed access checks, not a finding that Archilogic exposes information. No share URL or embed was created here. The availability of visibility controls should lead to an explicit sharing decision, with someone responsible for reviewing it when the audience, plan contents or connected application changes.

## GraphQL, SDK and agent access should follow application boundaries

The homepage describes a Floor Plan Engine SDK for embedded interactive models, GraphQL queries for spatial data and MCP access for agents. Those routes serve different consumers. A public viewer may need a narrow read-only model, while an internal application may need more detailed metadata. An agent connected to the spatial record may be able to retrieve information beyond what appears on a visible floor-plan screen. Define the intended scope before choosing credentials and exposing a feature.

Use a development model to verify the required query and rendering path, including what happens when a space is missing or a plan changes version. These are proposed development checks, not API calls made for this review. The saved promotional example establishes an integration concept, not a complete security or application architecture. The team still needs to determine how the frontend, backend and connected agent obtain the minimum information required for their respective tasks.

The pricing table mentions support levels and the publisher emphasizes response quality and large-enterprise use. Those claims can inform procurement questions, but they do not establish a response-time commitment for every plan or every issue. Clarify whether a support label means availability, target response or resolution, and how conversion questions differ from production incidents. Ask for the terms relevant to the selected package rather than relying on broad homepage language.
