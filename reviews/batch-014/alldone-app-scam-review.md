**Method:** Source-led desk review; no hands-on testing is claimed.

Alldone.app describes conversational task capture, linked project context and agent collaboration. This review examines approval states, connected accounts, recurring tasks, link sharing, hosted versus self-hosted operation, Gold allowances and export checks.

## Start with a bounded workflow rather than the chief-of-staff metaphor

The homepage's assistant metaphor covers capturing requests, organizing priorities and delegating project work. Those are useful categories, but a buyer should translate them into observable tasks. For example, recording a reminder is different from researching a vendor and sending a purchase request. Define the initial workflow, its permitted inputs and the point at which a person must review the result. A broad employee comparison does not establish the authority the assistant should have in a real business.

Use a small project with clear acceptance criteria before connecting every personal and company tool. These are proposed evaluation steps, not a project configured here. The goal is to determine whether the assistant reduces coordination effort without obscuring what happened. A natural-language confirmation should be checked against the underlying record or integration, especially when the next step affects another person or a system outside Alldone.


## WhatsApp and web interaction should share an understandable state

The publisher describes chatting with Anna through WhatsApp and using the same underlying tools directly in the web application. That can make capture convenient when a user is away from a desk. It also creates a need for consistent state: a task created through a message should be identifiable when the user later opens the project. An edit in the web interface should not leave the conversation suggesting that an obsolete plan remains current.

A useful pilot would create, revise and complete a small task through the available paths and inspect the resulting record. These are proposed checks, not interactions performed here. Confirm the actual channel setup, supported message types and account association through current documentation. The saved homepage establishes the intended experience but does not prove every synchronization or recovery behavior. Keep channel availability distinct from evidence that a specific action completed correctly.


## A unified inbox still needs clear task semantics

The feature page describes bringing tasks, calendar items and email-related work into one view, with postponement, recurrence and priorities. That can reduce the work of checking several places, but different items retain different meanings. Postponing a reminder should not be assumed to reschedule the external meeting, and checking off a personal task should not be mistaken for sending an email. Define what each action changes in the source system and what it changes only in the productivity interface.

During evaluation, inspect how the application labels a scheduled event, a follow-up and a work item awaiting someone else. These are proposed usability and integration checks, not outcomes observed here. A unified view is valuable when it preserves useful distinctions rather than making every object look equivalent. The source's all-in-one description does not establish that every connected system has the same lifecycle or completion rule.


## Human approval workflows deserve their own acceptance test

Alldone's feature page describes an engineer marking a task complete and the task then appearing for a manager to review or return. That is a concrete workflow distinction between work submitted and work accepted. A team should check that status, ownership and notifications reflect the approval stage. Otherwise the person doing the work may believe a task is finished while the manager still regards it as an unreviewed proposal.

Use a task with an explicit reviewer and exercise both acceptance and return for revision. These are proposed checks rather than a configured approval workflow. The source also describes suggested tasks and observed tasks, which should not be confused with assigning an obligation another person has accepted. Verify how a recipient understands the origin and expected action. A visible task in someone's inbox does not by itself establish agreement, authority or completion.


## Agent delegation should separate analysis from external action

The homepage lists agents associated with research, marketing, design, job search and other specialties, and says agents can act within projects. The names describe intended roles, not independently verified professional competence or permission to do everything within that topic. Define whether a request authorizes drafting, recommending, editing a project record or taking an external action. The more consequential the action, the more important it is that the interface shows what will actually happen.

A research result, campaign plan and published campaign are separate milestones. The assistant should not describe them interchangeably, and the user should be able to inspect the concrete result before an irreversible step where review is needed. These are proposed design requirements, not agent runs conducted here. The saved source does not establish the precise authority and review controls of every built-in agent. Evaluate the actual operation required instead of assuming that a role label guarantees an end-to-end service.


## Calendar and email access create an account-level boundary

The homepage describes connecting Google Calendar and Gmail for scheduling, inbox organization and drafted replies. These capabilities can make a personal assistant more useful, but they also require access to information and actions beyond a task list. Confirm which permissions are requested, which account is connected and how access is revoked. Reading a message, creating a draft, changing a calendar event and sending a reply should remain distinct actions in both authorization and reporting.

Use an appropriate test account and representative non-sensitive material when evaluating the path. These are proposed checks, not integrations made for this review. No mailbox or calendar was accessed. The saved marketing pages do not establish every token, retention or permission detail, so consult the applicable current documentation and policy. An all-in-one workflow should not obscure where private information originates or which external system remains authoritative.


## Recurring tasks need stopping and exception behavior

The feature page describes recurring tasks for humans and AI, including scheduled research. A useful recurring workflow needs more than a date rule: define the expected output, who reviews it and how the schedule is paused or retired. Repetition can magnify an unclear instruction or an expensive operation. A weekly research task is different from repeatedly performing an external action whose prior outcome is uncertain.

Evaluate a small recurrence with a clear stop condition and inspect what happens when the task cannot complete. These are proposed operational checks, not a schedule created here. Avoid assuming that a recurring task being listed means every run succeeded. The source does not document all execution, retry and notification guarantees in the saved material. A buyer should verify the behavior required for the actual workflow rather than extrapolate from a simple reminder example.


## Notes, backlinks and object chats can preserve context

The feature page describes creating tasks inline in notes, mentioning other objects and keeping chats attached to tasks or notes. These can reduce the work of reconstructing why a task exists. The important question is whether the link preserves the context the next person needs: the decision, the supporting material and the current action. A backlink can point to a discussion without establishing that everyone who can see the task may also read the linked information.

Test a small chain from meeting note to task to follow-up discussion, including a change in project membership. These are proposed context and access checks, not a test performed here. The review does not establish a particular permission defect. It recommends examining both navigation and visibility so the convenience of connected objects does not become either an unexplained access failure or an unintended sharing route.


## Link sharing needs object-level review

The saved feature page describes sharing objects through URLs, including content visible without signing up, while other passages emphasize private objects and selected team-member access. Those statements warrant a precise evaluation of the actual settings rather than a blanket assumption about every link. Decide which notes, tasks and goals should be public, shared with selected people or private before distributing their addresses.

Inspect a shared object as the intended recipient and in an appropriate signed-out context, and verify how sharing is withdrawn. These are proposed permission checks, not links opened for this review. The saved material does not resolve every combination of object type and visibility. A personal productivity system can contain sensitive work even if its content looks like ordinary task text. The correct sharing rule should follow the information and audience, not the ease of copying a URL.


## Hosted and self-hosted routes carry different costs

The homepage says source code is available for self-hosting and presents a self-hosted offer requiring the user's own AI API keys. That can support customization and operational control, but it does not establish zero total cost. Someone still needs to deploy, maintain, update and secure the environment, and model-provider usage can be billed separately. Compare those responsibilities with the hosted plan rather than equating free source access with a free managed assistant.

Review the actual repository license, installation requirements and applicable terms before relying on source availability for a commercial deployment. This article has not audited the code, interpreted the license or installed a server. The saved homepage's control and export claims are relevant questions for procurement, not a completed assurance that every integration and data path remains under the user's direct operation in every configuration.


## Gold allowances require a usage model

The captured homepage displays a Personal plan at $15 per month with 1,000 Gold for AI features, while a billing toggle also mentions annual savings. The saved text does not provide a complete conversion from each model operation to Gold. A buyer should therefore ask how the intended tasks consume the allowance, what happens when it is exhausted and whether additional usage requires another purchase or permission. A currency-like label alone is not a usable cost estimate.

The feature page also describes earning Gold and experience points through completed tasks. Confirm how any earned rewards relate to purchased or included AI usage rather than assume they are interchangeable. These are proposed commercial questions, not billing behavior tested here. No plan was purchased and no credits consumed. The review does not invent an overage rate or an unlimited-use promise where the captured source does not establish one.


## Productivity indicators are not business outcomes

Alldone describes goals, progress percentages, logged time, points and gamified achievements. Those can help organize personal work, but each measures a particular recorded behavior. An empty inbox can reflect postponement as well as completed work, and a task marked done does not necessarily mean a customer outcome occurred. Define what useful progress means for the project and avoid treating a reward or completion percentage as an independent performance assessment.

The feature page includes a coming-soon description for a happiness-tracking function among broader personal-growth material. Keep that roadmap status visible rather than report it as a released capability. This review has not verified current availability or measured well-being and makes no clinical claim. A productivity tool can help structure reflection while the user still decides whether the recorded activities support the goals that matter outside the application.


## Export and generated invoices need end-to-end checks

The homepage claims export in standard formats, and the feature page describes creating an editable Google Docs invoice from logged work. Those address different portability and business tasks. A downloadable export should be checked for the records and relationships needed to move elsewhere. A generated invoice should be reviewed for dates, quantities, rates and recipient details before it is treated as a request for payment. Logged time and billable time are not always identical.

These are proposed acceptance checks, not exports or invoices produced here. No document was sent to a client. The saved pages do not establish every export format or reconciliation behavior, so obtain the details relevant to the intended migration or billing process. A no-lock-in statement is useful positioning, but the evidence for portability is a recoverable, understandable output that can actually support the user's next workflow.
